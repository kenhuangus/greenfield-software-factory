# How to contribute

Thanks for helping improve Greenfield Software Factory. This repository is a
Codex (and compatible-agent) skill plus two Python helpers that persist and
validate factory runs. Read this file before opening a pull request.

## What belongs here

In scope:

- Skill routing and operating contract (`SKILL.md`)
- Phase, gate, worker, and recovery policy (`references/`)
- Durable schemas and templates (`assets/`)
- State and validation helpers (`scripts/factory_state.py`, `scripts/validate_run.py`)
- Codex skill metadata (`agents/openai.yaml`)
- Project docs (`README.md`, this file, copyright/license)

Out of scope unless the change is required by the skill itself:

- A product generated by a factory run (that lives in the target project)
- Host-specific absolute paths
- Weakening a gate, fingerprint, or evidence rule to make a demo pass

## Development setup

1. Fork [https://github.com/kenhuangus/greenfield-software-factory](https://github.com/kenhuangus/greenfield-software-factory) and clone your fork.
2. Use Python 3.9 or later. The scripts use only the standard library.
3. Install the skill by copying or cloning this tree into your agent's skill
   directory, keeping `SKILL.md` at the skill root.

No `pip` packages are required to run the helpers.

## How a change should be structured

Keep one home per rule:

| If you change | Also update |
|---|---|
| Phase names, gate names, profiles, or `state.json` shape | `scripts/factory_state.py`, `assets/schemas/state.schema.json`, `SKILL.md`, `references/artifact-contracts.md` |
| Feature-plan fields or slice statuses | `assets/schemas/feature-plan.schema.json`, `scripts/validate_run.py`, `assets/templates/feature-plan.json`, `references/artifact-contracts.md` |
| Worker report fields or lanes | `assets/schemas/worker-result.schema.json`, `assets/templates/worker-result.json`, `references/feature-delivery.md` |
| Template marker or required artifact names | `scripts/factory_state.py` `TEMPLATE_MAP`, `scripts/validate_run.py` `REQUIRED_ARTIFACTS`, `assets/templates/` |
| Authority, retry, or stop conditions | `references/authority-and-safety.md` and `references/recovery.md`, then a short pointer in `SKILL.md` if the orchestrator must see it |

Do not copy a long policy into a second file. Point at the file that owns it.

## Local checks

From the repository root (PowerShell or POSIX):

```text
python scripts/factory_state.py --help
python scripts/validate_run.py --help
```

Smoke a throwaway project. Use a new empty directory, not this skill repo:

```text
python scripts/factory_state.py init --project <empty-dir> --goal "cli smoke" --profile cli-library
python scripts/factory_state.py show --project <empty-dir>
python scripts/factory_state.py fingerprint --project <empty-dir>
python scripts/validate_run.py --project <empty-dir> --json
python scripts/validate_run.py --project <empty-dir> --gate --json
```

Expect `--gate` to fail on a fresh init: the templates still contain
`<!-- factory-template:`. That is intended.

Re-init of an existing `.factory/state.json` must exit 2. Skipping a phase,
marking a gate `passed` with no `--evidence`, and recording an artifact outside
the project root must also exit 2.

If you change `validate_run.py` or a schema, add or extend a failing-then-passing
check that covers the new rule. Hand-rolled validation in
`validate_run.py` must stay consistent with the JSON Schema files; if they
diverge, the schema is the documented contract for worker reports and the Python
checker is the contract for `state.json` and `feature-plan.json`.

## Coding rules

- Python 3.9+, standard library only, unless a new dependency is justified in
  the pull request.
- Keep path handling inside the project root. Reject symlinks and Windows
  junctions for `.factory/` the same way `factory_state.py` already does.
- Use atomic writes for JSON that a resumed orchestrator will reread.
- Do not edit history in `state.json` to hide a failure.
- Do not add host-absolute paths (`C:\Users\...`, `/Users/...`). Use skill-dir
  relative paths or well-known skill names such as `$playwright`.
- Match existing identifier patterns: `FR-###`, `NFR-###`, `AC-###`, `SLICE-###`,
  `BATCH-###`, `TASK-###`, `FIND-###`, `ASM-###`, `BLK-###`.

## Pull requests

1. Create a branch from `main`.
2. Keep the diff to one concern: policy, schema, helper behavior, or docs.
3. In the PR body, state:
   - the problem
   - the files that now own the rule
   - the exact commands you ran and their exit codes
4. Do not mark a quality gate, scan, or test threshold optional in order to get
   a green check.
5. Do not add AI authorship trailers to commits or PR text.

Open the pull request against
[https://github.com/kenhuangus/greenfield-software-factory](https://github.com/kenhuangus/greenfield-software-factory).

## Reporting issues

Include:

- Agent host (Codex, Claude Code, Grok, other) and whether workers were available
- Python version
- Command line and exit code
- Whether `.factory/state.json` existed, and `current_phase` / `status`
- A redacted `validate_run.py --json` payload when the bug is validation

Do not paste secrets, production data, or private repo contents.
